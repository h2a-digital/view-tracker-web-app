# Compact posts and grouped operational reviews

## Deployment order

1. Confirm the existing migration history. After the previously prepared migrations, manually run **only** `supabase/migrations/202611100002_post_pagination.sql` once in Supabase SQL Editor, before deploying this application version. Do not reset/reseed the database or rerun earlier migrations. This update has not run any SQL against production.
2. The migration adds indexes and a service-role-only read RPC. It does not rewrite posts, mappings, snapshots, compensation, existing functions or the schema-version value (still 5). Index creation can briefly lock writes; a five-second lock timeout aborts the transaction rather than wait indefinitely. On a busy or much larger database, schedule a quiet period; if it times out, the transaction rolls back and can be retried when quiet. No data-destructive operation is included.
3. Deploy through the existing Netlify procedure when ready. No new dependencies, environment variables, OAuth configuration or Cron schedule are needed. TikTok/Zernio, Instagram integrations, YouTube, polling and the compensation engine are unchanged.

## Posts data access

- Default: 24 posts per page; options 12/24/48. Grid and Table share the same database query and totals. Page navigation keeps search, app, campaign, order, size and view. Changing a filter, sort or size resets page 1. Selection survives switching Grid/Table; it is not persisted across a browser reload.
- `GET /api/posts` is admin-only and uncached. `read_post_page` applies filtering/counting/sorting and SQL limit/offset. Ordering uses publication time plus unique post ID for ties; public-view ordering uses the latest non-daily, non-supporting public observation and does not make those views payable. Concurrent imports can change counts/page boundaries; there is no frozen browsing session.
- Initial workspace reads and mutation responses return a browser projection: metadata, aggregates and recent preview rows, rather than the entire post/snapshot history. Post details fetch one record and its observations on demand; the client replaces the previous detail cache instead of accumulating all pages. Analytics returns aggregates computed server-side; finance totals are calculated server-side from the full authoritative workspace. A statement’s correction options are loaded only when its drawer opens.
- Server-side Overview, Analytics, review classification and monetary commands still use the existing full-workspace server loader. They do not ship its entire video history to the browser, but very large histories will eventually warrant SQL aggregates and narrower transactional writes. This update does not claim to eliminate all full-workspace server work.
- Landscape previews reuse cached URLs and existing image error/expiry fallbacks. No provider/image calls were added to pagination. Cards show four columns at >=1550px, three above 1100px, two above 650px, one on mobile. Overview keeps its three recent cards with shorter previews.

## Needs attention and routing

- Issues are grouped by account and cause: missing attribution, historical coverage, provider policy, promotion, format, data or evidence. Expanding a group fetches at most 12 records per page. Summary counts cover the full selected scope.
- Unassigned posts appear under **All apps**, since no app attribution can safely be inferred. For records with no app, campaign, rules or deadline, recorded discovery more than **168 elapsed hours** after publication, without earlier observations, now yields **Historical** before the missing-mapping check. This is a display-only discovery horizon, not an assigned financial window. Recorded first discovery, snapshot observation times and cached in-window observation times provide coverage evidence; today, latest account synchronization and provider freshness timestamps are not substituted. Earlier observations or discovery within 168 hours (including the exact boundary) keep the mapping-review path, even after later syncs. Records without usable recorded discovery/observation times remain under review. Assigned posts retain the existing configured tracking/follow-up classification and evidence-backed accepted posts retain payout readiness. Historical groups are excluded from operational counts and shown in a separate collapsed **Historical records** section; Posts and Analytics retain all records. Classification never accepts views, excludes records financially, assigns a campaign or changes a finalized payout. Unmapped records still cannot generate compensation; assigned historical records remain financially held until explicitly resolved using existing safeguards.
- **Connected** means provider access; **campaign mapping** means explicit attribution routing. Account cards and unmapped groups link to **Route posts**. Mapping defaults to now, remains within the creator’s assignment, and never changes existing imported posts. Backdating a new mapping does not retroactively assign already stored records. Individual reassignment remains an explicit, financially guarded action.
- Company-owned/test accounts require an explicit confirmation when creating a new compensation route. Existing mappings are untouched. Leaving brand content unmapped cannot itself generate creator compensation.
- **Exclude imported content** prepares up to 100 editable, unresolved IDs from that group and requires confirmation of the exact selected count. It is an explicit administrator decision, never an automated historical classification. Larger groups can be handled in successive confirmed batches. Expand first to inspect content; individual post details also supports excluding an unassigned record. Exclusion retains source records, snapshots, attribution and audit history, sets eligible views to zero and removes the records from the review queue. Already attributed/accepted records cannot use the unassigned exclusion command. Finalized/paid-month protections remain server-enforced; any invalid selection rejects the entire batch. No exclusions have been executed on production.
- Excluding records does not delete them or disable account discovery. New creator posts will continue to be discovered under the existing schedule.
- Neither public views nor missing/false ad flags prove organic eligibility. Completed tracking without organic/cutoff evidence can still require review. Bonuses and final payouts retain their existing approval requirements.

- Check browser Network: `/api/posts` returns at most the selected page size; dashboard responses contain only recent post rows/summary metadata, not all 54 posts. Confirm errors/timeouts leave usable controls.

Automated coverage includes PostgreSQL page/permission tests, query validation, bounded group expansion, historical classification, projection, rendering, routing consent and payout-safety tests. No browser was available to this development session, so interactive/responsive screenshot verification remains a manual check before deployment.

## Historical classification correction

The earlier historical check depended on an attributed deadline; unassigned Instagram imports have none. Grouping also prioritized missing mapping over the historical presentation state. The correction handles recorded late discovery independently for truly unassigned records and gives Historical priority in grouping. No SQL migration, environment change, data backfill or provider call is needed for this correction. Existing rows are classified on read; stored eligibility fields, observations, routing, synchronization behavior and payouts are untouched. Refresh the dashboard after running the updated code. No production data was modified.

# Direct integrations: lifecycle and safe production rollout

Prepared November 8, 2026. No live services were changed. The current app requires schema **5**. Google/Meta approvals and live entitlement tests remain external prerequisites, not something code or an environment flag can grant.

## What is enforced

- Existing TikTok/Zernio source data, credentials, rules, America/New_York accounting, 168-hour windows, discretionary bonus approval and caps are unchanged. Facebook remains outside Versel's bonus.
- An authenticated worker invocation runs a database retention sweep, then at most one remote revocation and one source-check batch (50 videos) within a **12-second shared maintenance budget**. The entire worker retains its shared 45-second provider budget and 60-second function setting. Remaining time handles up to eight tracking jobs. Additional maintenance batches are picked up by later five-minute calls. No second Cron schedule is required.
- Connected direct accounts have authorization and retained-video availability checked approximately daily, including videos whose eligibility windows are closed. YouTube checks use `channels.list(mine=true)` plus `videos.list` batches; Meta checks the authorized resource and individual retained objects. Metadata is refreshed without changing publication timestamps, eligibility deadlines or historical metric snapshots.
- A successful account identity request does not mark failed video requests successful. YouTube deleted/nonpublic/mismatched videos are erased. Meta inaccessible-object failures are retried rather than guessed to be deletions; unresolved sources are erased by the hard deadline.
- The application deliberately keeps source data for **at most 90 days from publication**. Metadata and authorization must be successfully checked within **29 days**, providing a buffer before YouTube's 30-day requirement. This is a conservative application policy, not a claim that Meta specifies a universal 90-day retention period. No flag extends these limits to the optional YouTube amendment's longer maximum.
- Disconnect, a creator deletion request, or detected revoked credentials immediately erases applicable local direct-provider sources. Signed Meta deauthorization/deletion callbacks do the same. Revocation credentials and stale worker/source leases are invalidated atomically. Optimistic revisions prevent an in-flight sync from restoring erased data.
- A provider revocation outbox retries network/rate/server failures with exponential backoff. It uses Google's `POST https://oauth2.googleapis.com/revoke` (form body) or Meta's `DELETE /{app-scoped-user-id}/permissions` with a user token and app-secret proof. Only encrypted revocation material remains, for at most **24 hours**, inaccessible to tracking. Success removes it immediately; expiration removes it and raises an operations warning requiring provider-side confirmation. Google revocation may invalidate other channels sharing the user's project grant. Meta local deletion also covers accounts linked to the same authorizing subject; revocation can remove their shared permissions.
- The Meta user token is retained encrypted only to support grant revocation. Legacy direct Meta credentials created before this release may lack that token and subject mapping: reconnect those test grants before onboarding; remove old app permissions in Meta settings if remote revocation cannot be confirmed. No old token is fabricated.
- Creator deletion links expire after 90 days and require explicit same-origin POST confirmation. The administrator can issue a new link using **Social accounts → Creator deletion link**. A creator sees the initial private link after OAuth, without receiving a dashboard session.
- Meta callbacks authenticate `signed_request` using HMAC-SHA256 and `META_APP_SECRET`, validate the algorithm/user/timestamp and match a private keyed subject fingerprint. Older callbacks cannot erase a newly reauthorized grant. Callbacks return an opaque confirmation code and status URL only after the database transaction completes. Database failures return a retryable 503. Invalid signatures are rejected. Replays are idempotent.
- Receipt status exposes only completion state/time and expires after **30 days**. It does not reveal creators, account IDs, videos or whether an unknown Meta subject ever connected. A completed receipt means local source deletion, not deletion of original social-platform content or guaranteed completion of remote grant revocation.

## Financial history and erasure boundaries

Erasure removes raw snapshots (including manual/CSV copies associated with a direct account), captions, external video IDs/URLs, precise publication/deadline timestamps, eligible-view totals, tracking caches, review evidence, free-text approval notes, source-bearing sync diagnostics, correction evidence and calculation fingerprints. View counts in settled statement lines become `null`, visibly labeled **Source erased**. Internal tombstone IDs are not external platform identifiers.

Settled dollar amounts, payment status/references, company-entered creator/contract records, accounting month and monetary allocations remain. Erasure cannot change settled money. Ordinary writes still cannot mutate finalized/paid statements. After erasure, a statement cannot be recalculated through a new performance correction because the source inputs no longer exist; approved monetary corrections may still be settled. Draft approvals/totals are invalidated and recalculated from surviving sources; removed sources cannot become newly payable. A new connection after complete account erasure requires a new registration and fresh consent.

These company accounting records are **not asserted to be anonymous or exempt from privacy law**. Establish the company's lawful accounting retention schedule and basis before external onboarding, and keep contract records independent of API exports. No blanket legal-hold exemption is applied to API data. If a regulator/provider requires deletion of additional derived records, resolve that scope with them; the application does not silently retain API counts under an accounting label.

The application cannot erase previously downloaded CSVs, screenshots, database dumps or third-party backups. Restrict backup/export access, remove exported source copies when a request is processed, and configure backup retention/removal consistent with the deletion deadline and provider requirements. Do not create indefinite source archives.

Before restoring an old backup, export the **current** internal-ID-only erasure manifest from `private.erased_accounts` and `private.source_erasure_log` into a separate restricted recovery record. After restoring into an isolated environment and applying missing migrations, replay it **before enabling dashboard access, workers or OAuth**:

```sql
-- Replace with internal UUIDs from the current manifest; never platform IDs.
select public.reapply_source_erasure_manifest(
  array['ACCOUNT-UUID']::uuid[],
  array['POST-UUID']::uuid[]
);
```

Use empty `array[]::uuid[]` where appropriate. The restore RPC filters to direct-provider accounts/posts and preserves settled money. Do not restore a pre-deletion backup directly into service. If no current manifest is available, keep it isolated until requests and erased records have been reconciled.

## Rollout checklist (manual; no live actions were performed)

1. **Prepare a recovery point and cutover window.** Record current schema (`select public.read_dashboard()->>'schemaVersion';`), TikTok account/connection identifiers, snapshot counts and finalized/paid amounts privately. Ensure the recovery policy above is in place. Do not publish exports containing source data. Finish the production build before the window.
2. **Configure Netlify production variables before release.** Reuse existing `NEXT_PUBLIC_SUPABASE_URL`, public Supabase key, server-only Supabase secret/service-role key, `ADMIN_EMAIL`, canonical HTTPS `APP_URL`, `ZERNIO_API_KEY` and `CRON_SECRET`. Add the existing direct-integration variables from `.env.example`: `OAUTH_TOKEN_ENCRYPTION_KEY` (64 random hex characters), Google client ID/secret, Meta app ID/secret/explicit supported Graph version, login configuration ID if required, and a monitored `PUBLIC_SUPPORT_EMAIL`. Do not rotate the encryption key casually; it also keys private subject matching. Keep secrets out of `NEXT_PUBLIC_*`, source control, redirects and `netlify.toml`. Retain Node 22 and the existing Next.js adapter setup. Keep previews isolated from production credentials.
3. **Leave verification switches conservative.** `YOUTUBE_ANALYTICS_POLICY_APPROVED=false`, `INSTAGRAM_ORGANIC_VIEWS_VERIFIED=false`, `FACEBOOK_ORGANIC_VIEWS_VERIFIED=false` until the corresponding approvals/definitions have been validated. The lifecycle does not need a new secret or scheduler.
4. **Pause the existing Supabase Cron job and stop local/old worker processes.** Avoid admin edits during the cutover. Save the job ID so you resume it rather than create a duplicate. Keep the old application unavailable during the schema/app version transition.
5. **Apply only missing migrations, in order.** On schema 3, run `202611080003_direct_integrations.sql` (v4), then `202611080004_provider_lifecycle.sql` (v5), each complete file once in Supabase SQL Editor as `postgres`. On schema 4, run **only 004**. On schema 5, skip both. If still at 2, apply the previously prepared operations migration 002 first. Never rerun 001/original initialization, reset, reseed or delete existing records. Both new migrations are transactional; 004 registers checks but does not erase records merely by being applied.
6. **Verify the database before deployment.** Confirm schema 5 and America/New_York; compare the TikTok connection, snapshots and settled dollar amounts with step 1. The old application is not runtime-compatible with schema 5: data compatibility does not mean mixed old/new app versions are supported. If deployment is delayed, keep Cron paused. Roll forward to the matching app; do not roll back by reinitializing data.
7. **Deploy the prepared app to the canonical Netlify HTTPS origin.** Log in only as the existing authorized administrator; public signup remains disabled. Verify the unauthenticated dashboard/API remain blocked, OAuth information/privacy/deletion pages load, and an unauthenticated worker POST returns 401. No new Supabase Auth users are needed for creators. Retain Supabase's existing admin user/allowlist; update Auth site/redirect origin only if the production domain changed.
8. **Resume the existing Cron job.** Keep `POST https://YOUR-DOMAIN/api/internal/jobs`, schedule `*/5 * * * *`, the Vault `ugc_worker_url`, and matching `ugc_cron_secret`/Netlify `CRON_SECRET`. If the origin changed, update only the Vault URL. Do not add a second schedule or enable Netlify Scheduled Functions. Wait for two successful authenticated calls and inspect **Needs attention → Automation health**, lifecycle counters, queue state and per-account sync diagnostics. A retention/queue failure is reported as a failed worker, not silently acknowledged.
9. **Set up Google Cloud in testing first.** Enable YouTube Data API v3 and YouTube Analytics API. Configure External consent, authorized domain and public homepage/privacy contact, Web application OAuth client, and test users. Request only `https://www.googleapis.com/auth/youtube.readonly` and `https://www.googleapis.com/auth/yt-analytics.readonly`. Register exactly `https://YOUR-DOMAIN/api/oauth/youtube/callback`. Publish the appropriate consent status and complete applicable branding/sensitive-scope verification before external unattended production; Testing refresh tokens ordinarily last seven days. Resolve YouTube analytics/derived-metric/cross-owner aggregation acceptance separately before enabling the compensation flag. Creator deletion links and provider account-settings revocation cover the deletion flow; no Google push-revocation application is assumed configured.
10. **Set up Meta in development first.** Use Facebook Login for Business and the company's app/Business Portfolio. Instagram requires a Creator/Business account linked to a Page; Facebook supports Pages. Set homepage/privacy URLs and register OAuth redirects `https://YOUR-DOMAIN/api/oauth/instagram/callback` and `https://YOUR-DOMAIN/api/oauth/facebook/callback`. Configure **Deauthorize callback URL** `https://YOUR-DOMAIN/api/oauth/meta/deauthorize` and **Data deletion callback URL** `https://YOUR-DOMAIN/api/oauth/meta/delete-data`. The human instructions page remains `https://YOUR-DOMAIN/integrations/delete-data`; it is not the signed-request callback. Instagram permissions: `pages_show_list`, `pages_read_engagement`, `instagram_basic`, `instagram_manage_insights`. Facebook permissions: `pages_show_list`, `pages_read_engagement`, `read_insights`. Set the login configuration ID where required. Complete applicable Advanced Access/App Review, business/tech-provider verification and Data Use Checkup requirements before authorizing external creators. API-version-dependent Facebook metrics still require an actual Page pilot.
11. **Test the full lifecycle using disposable creator-owned test grants.** Connect the exact registered channel/Page/Instagram identity through an invitation in a browser without an admin session. Publish natively, confirm discovery through Cron, and observe later counter snapshots. Test wrong-account consent, revoked Google grants, revoked Meta permissions, and Meta's real deletion/deauthorization test callbacks. Test a creator deletion link with disposable source data: snapshots/evidence should disappear, source lines should read erased, settled money must remain, and remote revocation should complete. Old callbacks and a second deletion request must not restore anything. Never erase the existing TikTok pilot to test this feature. Do not falsify production timestamps to simulate retention; automated tests cover expiration.
12. **Enable external onboarding only after the provider gates pass.** Keep uncertain organic/cutoff evidence out of approval. Confirm manual bonus/final payout approval, Facebook exclusion and monthly cap. Verify the company retention/contact policy and remove old source exports. Monitor Netlify Usage & billing: the scheduler is still about 8,640 requests per 30 days, with extra compute only when maintenance/tracking is due; the Free credit allowance is not a throughput guarantee. Monitor stale Cron calls, source-check errors, failed revocations and provider review/usage notifications. Hosting suspension prevents scheduled deletion, so investigate stale automation promptly rather than relying on free hosting without monitoring.

## Policy references and verification limits

- [YouTube developer policies III.E.4](https://developers.google.com/youtube/terms/developer-policies): authorization/deleted-video checks, metadata refresh/deletion and requested deletion within seven calendar days.
- [YouTube derived metrics/storage amendment](https://developers.google.com/youtube/terms/derived-metrics-policy): additional accepted uses and conditional extended statistics retention; no automatic acceptance is implied.
- [Google OAuth revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke): grant scope and revocation endpoint.
- [Meta deletion callback](https://developers.facebook.com/docs/development/create-an-app/app-dashboard/data-deletion-callback/) and [Meta manual flow/deauthorization](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/): app callback registration. Meta's documentation endpoints were rate-limited during this review; validate the actual app's dashboard instructions and real signed-request test before switching it live.
- [Meta official User SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/user.py): user permissions DELETE endpoint. No unsupported Page-token refresh mechanism is invented.

Local fixtures and native PostgreSQL checks validate behavior and migration compatibility, not Google/Meta production entitlement, legal approval, actual Netlify credit consumption or the availability of an organic metric.
